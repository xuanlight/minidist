# ADR-0001: HTTP + JSON 先行，不引入框架

- 日期：2026-11-07
- 状态：accepted
- 决策者：Sergio Shen
- 相关：[Week 2 文档](../week2.md)

## 背景

MiniDist 的第 1 个可用版本需要对外接口，让 CLI 与其他程序读写 KV。
本周（第 2 周）的目标是走通 `handler → service → store` 的分层，并建立统一错误模型，
而不是做一个生产级 API 网关。

约束：

1. **只用标准库**——计划书原则：不引入"看起来高级"的中间件，除非当前阶段非它不可；
2. **一周内完成，且必须可测**——用 `httptest` 覆盖状态码矩阵，不依赖真实端口；
3. **第 5 周会引入自研 RPC**——HTTP 层的结构要能被 RPC 层复用，不能成为包袱。

## 决策

使用 Go 标准库 `net/http` + JSON 作为第 1 版对外接口：

```text
PUT    /v1/kv/{key}     body: {"value":"..."}      → 204
GET    /v1/kv/{key}                                → 200 {"key","value"}
DELETE /v1/kv/{key}                                → 204
GET    /healthz  /readyz  /stats
```

错误体统一为 `{"error":{"code","message","request_id"}}`，`code` 是客户端可程序化分支的稳定标识。

## 备选方案

| 备选 | 优点 | 为什么不选（本周） |
|---|---|---|
| **Gin / Echo** | 路由、参数绑定、中间件生态开箱即用 | 本周的目标就是从零理解路由与中间件的工作方式，框架恰好会把它们封装掉；它的收益在生态，而本周没有生态问题要解决 |
| **gRPC + protobuf** | 强类型契约、性能好、天然支持流式 | 它的回报来自多语言客户端和强类型契约；本周只有 Go 一个客户端，`curl` 调试的价值更高，引入 IDL 工具链只会分散时间 |
| **自定义二进制协议** | 编解码开销最低 | 编解码不是本周的瓶颈（实测 QPS 受限于客户端与内核），而不可读的线上格式会显著抬高排障成本 |

## 后果

### 好处

- **零依赖**：`go build` 得到单一二进制，没有版本冲突和供应链风险；
- **可调试**：`curl` 直接验证，线上排障不需要客户端工具；
- **概念不被隐藏**：路由匹配、中间件顺序、状态码映射、超时控制全部手写，
  这些正是第 5 周 RPC 层要复用的结构。

### 代价

- **传输层全部自建**：路由、参数校验、错误映射、超时与关停都要自己写并自己测，
  每个新接口都要重复一遍"解析 → 校验 → 映射错误"；
- **没有框架生态**：没有 OpenAPI 生成、没有校验 tag、没有统一的分页/排序约定；
- **JSON 编解码是真实成本**：同一轮压测中 PUT 的 QPS 比 GET 低约 10%
  （187,853 vs 208,135），主要来自请求体解码与 key 校验；GET 侧则多一次响应编码。
> 接口选型的完整论证见 [ADR-0001](adr/0001-http-json-first.md)。

### 风险

- **两套协议的错误语义漂移**：第 5 周加入 RPC 后，HTTP 的错误码与 RPC 的 status code
  可能各自演化，客户端看到的行为不一致。
  应对：领域错误仍然只在 `service` 定义，HTTP 与 RPC 各自只有一个映射函数。

## 重审触发条件

出现以下任一情况时重新评估本决策：

1. 出现多语言客户端需求（例如 Python / Java SDK），JSON + 手写客户端开始重复劳动；
2. 出现只能靠流式或双向通信表达的接口需求（如 watch / 订阅推送）；
3. 单个请求的编解码开销成为 p99 的主要贡献项（例如用 pprof 看到 JSON 占比超过 20%）。
